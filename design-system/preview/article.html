Da issue ao agente: arquitetura antes de automação.

Uma página-modelo para avaliar hierarquia, links, blocos de código, notas e o ritmo de leitura. Este artigo é fictício e não deve ser publicado como conteúdo editorial final.

Rafael Gomides•Engineering notes / Demo

Quando uma atividade é encaminhada a um agente, o principal risco nem sempre é a execução: é a perda de contexto, de fronteiras e de uma definição objetiva de conclusão.

1. Comece pelo contexto

Antes de delegar, descreva o problema, o resultado esperado e as evidências que permitirão verificar a entrega. Isso reduz a ambiguidade e evita trabalho tangencial.

Princípio de design

Callouts destacam decisões ou advertências. Não substituem a hierarquia principal do texto.

2. Defina um contrato claro

Uma interface pequena torna as obrigações explícitas. O exemplo em Go abaixo demonstra como os blocos de código devem se comportar em telas grandes e pequenas.

type TaskRequest struct {
    Goal       string
    Scope      []string
    Acceptance []string
}
func (r TaskRequest) Valid() bool {
    return r.Goal != "" && len(r.Acceptance) > 0
}

O texto TaskRequest.Valid() deve permanecer legível e acessível por teclado, inclusive dentro de parágrafos e blocos longos.

3. Torne os trade-offs visíveis

Uma decisão técnica deve registrar o que se ganha, o que se perde e por que determinada alternativa foi escolhida.

Legibilidade é uma propriedade do sistema, não um acabamento final.
  • Explicitar os limites da alteração.
  • Manter decisões junto das evidências.
  • Não ampliar o escopo sem justificativa.

4. Encerramento

Um bom artigo técnico deixa o leitor com critérios aplicáveis, referências verificáveis e um caminho concreto para colocar o raciocínio em prática.
